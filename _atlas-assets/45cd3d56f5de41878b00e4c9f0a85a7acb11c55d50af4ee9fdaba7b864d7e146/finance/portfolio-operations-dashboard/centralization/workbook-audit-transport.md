# Workbook evidence transport

The client uploads the exact serialized audit JSON and exact original workbook as separate byte streams, using 192 KiB raw chunks (at most 262,144 base64 bytes plus a small JSON envelope per request). SHA-256 hashes cover each chunk, both complete streams, and the canonical manifest. The server checks declared lengths and stream hashes before creating the existing immutable audit record and binding its community in one transaction. Default request UUIDs derive from the uploader, community and manifest so an interrupted save resumes with the same ID after a page reload without local financial storage. Explicit request UUIDs remain supported. Request IDs are scoped to the uploader; replay returns the same audit, and reuse with changed evidence or scope fails.

The following reforecast import envelope is also chunked. It otherwise repeats the sheet, cell, line, planning and schedule inventories and could recreate the oversized request failure immediately after a successful audit save. Finalize calls the existing authorized reforecast import function inside the transaction and compares its saved payload. The client reads both audit/source streams and the intake envelope back in bounded chunks and verifies their exact bytes and hashes. Historical audit references remain readable.

`atlas-central-client.js` records UTF-8 request bytes, elapsed milliseconds, sanitized UUID request identity, HTTP status, transport classification and allowlisted gateway correlation values (`sb-request-id`, `x-request-id`, `cf-ray`). It never adds workbook data, URL query parameters, credentials, or arbitrary response headers to diagnostics. No-response, HTTP error, invalid response, cancellation and timeout are distinct; response-body timeouts retain received gateway information. Requests finish within a client deadline and can safely retry the same request ID.

Privileged functions live in `atlas_private`; public RPC wrappers run as invokers. Staging tables have RLS, no browser table privileges, and immutable chunks/manifests. Every write/replay/read rechecks current account and community authorization. Original ownership does not bypass revoked community access or an inactive account. Four unfinished saves and 256 MiB aggregate declared bytes are reserved under an owner-level transaction lock across both protocols. Existing-request retries use their original reservation. Successful finalization releases the unfinished reservation. The explicit recovery API lists caller-owned unfinished saves and cancels a selected transfer after rechecking authorization. Cancellation retains an immutable manifest/request tombstone, removes only temporary chunks, and releases its reservation. Finalized audits/imports cannot be canceled. The tombstone supplies a stable new retry UUID, so resuming the previous request after cancellation or reload works without retaining an unusable request. There is no automatic expiry or deletion of finalized evidence.
